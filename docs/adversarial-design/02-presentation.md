## 1. 现状展示形式的三大最大缺陷（对抗性排序）

> 这里刻意避开审计已修掉的 chrome 问题（导航折行、缺 aria-current、目录折叠等），只挑**U 系列没有触及、且是「信息形态」层面**的三条。

### 缺陷一 · 单介质：全站散文 + 表格，无任何非文本/图形化承载

**证据**：

- 全 dist 0 个 `<svg>`、0 个 `<canvas>`、0 张正文 `<img>`、0 字节 `<script>`（§0.1 复算）。
- 条目正文是唯一内容形态：`src/pages/[...slug].astro:243-245` 的 `<div class="entry-body"><Content /></div>` 直接吐出 markdown 渲染结果；五节闸门把每条都切成「怎么做/说人话/收益/来源/备注」五个散文 `<section>`（审计 A 附录：122/122 条五节齐全）。
- 唯一的结构化表达是表格：260 张（正文 256 + 对照 4；审计时点旧计数为正文 123 张、其中 26 张 `table-cards`，内容后续扩充后增到 256），而表格**本质是把散文按行列重新排版**，不改变「读文字」这一种认知通道。

**为什么这是最大缺陷**：站的最高频信息是**数字与关系**——跌幅、恢复年数、回本倍数、仓位比例、偏差严重度排位。这些信息用一张图/一条可视化 2 秒读完，用散文要 20 屏。`凯利公式仓位下注多少`、`一笔数学亏一半要赚一倍才回本`、`哪些偏差真的会亏钱十二个现象按证据排位` 这类条目，其内容本身就是**函数/排序/阈值**，现在被压成散文步骤。整站没有一个 SVG 折线/条形/分布，等于把「可一眼懂的」主动翻译成「要逐行读的」。

### 缺陷二 · 122 条等肩高：没有「快慢双通道」，注意力层级只有「读」没有「扫」

**证据**：

- 每条条目页都是同一渲染骨架（`[...slug].astro:153-246`），正文长度从 74 行到 442 行 HTML 不等，但**投入结构相同**：读者要么通读、要么退出，中间没有「5 秒结论 → 30 秒骨架 → 足时精读」的阶梯。
- 真正有「5 秒层」的只有 29 条：`hasQuick = Boolean(d.lede && d.when && d.keyNumber && d.maxRisk)`（`[...slug].astro:99`），93/122 条的速览卡回落到「收益档位 · 量纲」「钱/时间/毅力」这种**信息量低于标题本身**的占位文案（sticky 结论条 `[...slug].astro:188-190` 同样回落为「收益档位 X · 量纲 Y」）。
- sticky 结论条（U-1）只把标题+等级+一个大数字+最大风险粘在顶部，**它没有生成任何新信息**，只是把已存在字段搬到 sticky 位；对 93 条无字段的条目，它顶着一个「收益档位 大 · 量纲 亏损」的空标语。

**为什么这是最大缺陷**：移动端注意力是 3–8 秒。这个站把 122 条全部做成了「要求通读」的说明书，而没有做「可扫读的不等式/结论/数字矩阵」。U-1/U-2/U-3 恰好**全都在增补导航与信号、没有制作「扫读层」**——四色 tag 告诉你「这条是理念」，但不告诉你「这条的结论是什么数」。注意力层级仍是一维的。

### 缺陷三 · 决策类内容被「文本化」：天然交互的条目被打平为步骤文

**证据**：

- 硬约束 `src/styles/global.css:3-4`「约束：零 JS」+ 实测全站 0 `<script>`；`docs/audit/02-presentation.md:104`（P-12）原文「全站 0」「无搜索框」已被 P1-10 以**零 JS 拼音跳格**接住（`src/pages/aliases.astro:10-104` 分组渲染，队长裁定方案 A）。
- 但「零 JS」只解决了「检索」这一个交互；下列条目本身的**信息本质是交互的**，现在全部被打成散文步骤：
  - `凯利公式仓位下注多少`——本质是 `f = p − (1−p)/b` 一个公式 + 一张「胜率×盈亏比→仓位」查找表；
  - `一笔数学亏一半要赚一倍才回本`——本质是一张「跌幅→回本所需涨幅」单调函数表（−10%→+11.1%，−50%→+100%，−90%→+900%）;
  - `事前检查清单下单前强制回答五问` / `亏钱理念自查表我最危险的三条`——本质是 checkbox/打分器，回答完得到「我的危险分」;
  - `哪些偏差真的会亏钱十二个现象按证据排位`——本质是「按证据强度排序的热图/横条」;
  - `先分清三种钱保命钱闲钱搏钱` / `修行七件事顺序比清单重要`——本质是分流决策树（你的钱属于哪一种？）。
- 这些条目的「怎么做」节，让读者**在心里跑一个计算器**：拿笔算凯利、脑子里回本曲线、逐个勾五问，再把结果记在脑子里。而这一切在零 JS 约束内**仍然可以做**（见 R-B：构建期预计算 + 静态查找表），唯一没做的是「把心算变成查表/勾选」。

**为什么这是最大缺陷**：它暴露了 U 系列的边界——U-2 破了「无检索」、却把「检索」定义为「找条目」；条目**内部的「做」**仍被文本化。一个自称「逃生指南」、承诺「能照着做」的站，其最高价值条目（决策/计算类）恰恰是最不该用长文交付的。

## 2. 重构方案（R-A ~ R-E）

> 排序 = 建议优先级。每条给：解决哪个缺陷 → 页面草图（伪结构）→ 涉及文件 → 成本（小/中/大）→ 预期收益 → 是否破零 `<script>`。
> 与已有 U 系列的关系在每条末尾标「与 U 系列的关系」，确保是「在其上对抗」而非另起炉灶。

### R-A · 按 `layer` 分型渲染协议（元方案，其余方案的地基）

- **解决**：缺陷二（等肩高）+ 缺陷一。`layer` 字段（理念/执行/档案/工具）已经对 122/122 条必填（`topic/[domain].astro:61-71` 按层分组、`global.css:487-499` 四色已落地），但它现在只用于「加色点」，没有决定「这一型条目该用什么形状」。激进主张：**让 layer 决定默认形态**，长文只保留给「理念」。
- **分型矩阵（默认形态；占比为本次实测 `grep -h '^layer:' src/content/escape/*.md | sort | uniq -c`）**：
  | layer | 实测条数 | 默认形态 | 长文是否默认折叠 |
  |---|---|---|---|
  | 理念 | 43 | 保留长文（五节不动） | 否，全文展开 |
  | 执行 | 35 | **清单/流**：步骤即卡片，一步一屏；「说人话」前置为结论；正文步骤转 `<details>` 分步展开 | 是，只默认展开「结论 + 步骤卡」 |
  | 档案 | 37 | **数据卡片/档案卡**：数字矩阵 + SVG/条形（正好接 R-C：十八条股灾、大师业绩全是档案层）；正文转「档案全文」折叠 | 是 |
  | 工具 | 7 | **工具卡网格**：外链/入口按钮（查\* 类天然是「去哪里点哪」），正文折叠为「怎么用」 | 是 |

  > 注：档案层（37 条）不是「少」，而是第二大层、且**全部是数字最密集的一层**（历史股灾 + 大师业绩）——这让 R-A 与 R-C 天然合流：档案层默认形态=「数字卡 + SVG」，是所有层里收益最先、最该动的一层。

- **页面草图（执行层为例）**：
  ```
  ┌ sticky 结论条（沿用 U-1，结论前置）────────────┐
  │ 证据 A · 最大风险 …（旧）                      │
  ├─ 5 秒层：结论一句话（说人话，大字号）──────────┤
  ├─ 30 秒层：步骤卡 ×N（每张卡 = 一步：动作/判据）│
  ├─ N 分钟层：<details> 完整五节正文 ────────────┤
  └ 底部同域导航（沿用 P2-C4）──────────────────┘
  ```
- **涉及文件**：`src/pages/[...slug].astro`（按 `layer` 走不同分支渲染；需要把「说人话」节从 markdown 里抽出来放到结论层——见 `src/lib/headings.mjs` 现在按 h2 拆 section 的能力，可再抽 per-section 文本）；`src/styles/global.css`（新增 `.layer-执行/.layer-档案/.layer-工具` 的形态类，不是颜色类）；可能的 `src/lib/*.mjs` 构建期抽取。
- **成本**：**中**。闸门体例（五节/四段式/机器验）必须保持不动（`docs/content-v2-spec.md` + `verify-escape-guide.sh` 不变式），R-A 是在不破坏五节的前提下改**渲染外壳**——需要谨慎处理「把说人话提到结论层」是否会破坏「来源节/备注节必须在正文」的语义。**风险点在此，交主编确认是否允许渲染层重排节序。**
- **预期收益**：**高**。这是唯一一个直接回答「122 条全是一样长文」的方案；90 条非理念条目从「通读」变成「扫→点→展开」，移动端留存与「照着做」转化是最直接的受益面。
- **破零 JS**：**不破**（纯构建期 + CSS + `<details>`）。
- **与 U 系列的关系**：U-3 的四色是 R-A 的「色」，R-A 是 U-3 的「形」——四色答「哪一层」，分型答「这层应该长什么样」。U-1 sticky 条成为 5 秒层的承接，不废弃。

### R-B · 零 JS 决策流 + 预计算查找表（把「算」还给读者）

- **解决**：缺陷三。决策/计算类条目 = 「输入我 → 得到我的结论」，零 JS 内可用**构建期预计算 + `<details>` 分步 + 纯 CSS 单选**替代。
- **页面草图（凯利公式为例）**：
  ```
  ┌ 结论先给公式：f* = p − (1−p)/b ────────────────┐
  ├ 三步分流（details 级联式）：
  │   ▸ 第①问：你能估胜率 p 吗？→ 能 / 不能
  │     （不能 → 「不估就不要下注，去读 别满仓别单吊」）
  │   ▸ 第②问：盈 s 亏 r 是多少？→ 填进来
  ├ 静态查找表（构建期预计算 matrix）：
  │   胜率\盈亏比 │ 1:1 │ 2:1 │ 3:1 │
  │   50%         │ 0%  │ 25% │ 33% │
  │   60%         │ 20% │ 40% │ 46% │
  │   …（每格是算好的 f*，标「超过 25% 建议减半」风险带）│
  └ 完整五节正文 <details> 折叠 ─────────────────────┘
  ```
- **同样可预计算/查表化**：回本曲线（跌幅→所需涨幅单调表，可顺手做成 R-C 的 SVG 曲线）；三种钱分流（保命/闲钱/搏钱 → 对应去读哪条）；五问自查（5 个 `<input type=checkbox>` + CSS `:has()` 计数——**纯 CSS 可数勾选数并不需要 JS**，`global.css:600` 已经用过 `:has(.concl-bar)`，浏览器支持门槛已在此站接受范围内）。
- **涉及文件**：`src/pages/[...slug].astro`（对决策类条目加一个 `calc-panel` 前置块，数据来自 front matter 新可选字段或构建期从正文抽取）；`src/data/*.json`（新增决策矩阵数据，如 `calculators.json`，与 `compare.json` 同风格、可被 verify 守卫）；`src/styles/global.css`（panel/查找表/checklist 样式）。**新增交互类条目的判定清单（哪些条目走 R-B）需内容侧出清单——可交 t1 或主编。**
- **成本**：**中**（每个决策类条目要一次性造矩阵/流程数据；一次性投入，之后 4 类条目共用一套面板模板）。若只做「跌幅→回本」和「凯利」两张最高频表，可切片**小**。
- **预期收益**：**高**。把 5 条「心算」条目从「读一篇」变成「查一行/勾五下」，是收益/成本比最高的一类。
- **破零 JS**：**不破**（纯 CSS 单选/勾选 + 构建期预计算 + `<details>`）。注意 `:has()`/`:checked` 计数属渐进增强，不支持的老内核退化为「无法计数但可目视勾选」，信息仍可达。
- **与 U 系列的关系**：与 U-2 同源——U-2 是「找条目的交互」，R-B 是「条目内的交互」，是 U-2 的下一跳。

### R-C · 内联 SVG 数据可视化（图表层，零脚本）

- **解决**：缺陷一。全站 0 SVG 是事实；而十八条股灾（跌幅 + 恢复年数）、大师业绩、十二偏差排位、回本曲线这四类数据天然是图。现在它们全躺在 `compare.json` 的 `rows[].c[]`（可 grep 的结构化 cells）和正文表格里。
- **页面草图**：
  ```
  「十八场股灾」域页/对照表页新增：
  ┌ 横向发散条形：一场一条，x=跌幅%，色=证据等级 ────┐
  │ 1637 ██░░  1987 ██████  1929 ████████  …        │
  │ 长度=跌幅，标签=恢复年数（如「−89.19% × 25.2y」）│
  └────────────────────────────────────────────────┘
  回本曲线（条目内）：一条从 (0,0) 陡升的凸曲线，标 −50%→+100% 点。
  ```
- **实现（不破零 JS）**：构建期从 `compare.json` / front matter 生成**纯静态 `<svg>` 内联**（无 `<script>` 子孙、无外链，`viewBox` + `text` 元素，颜色取 CSS 变量）。静态 SVG 也是「文本」，但有图层的视觉通道；SSR 阶段算好坐标，浏览器零执行。
- **涉及文件**：`src/lib/charts.mjs`（新增，纯构建期：读 compare.json → 输出 svg 字符串）；`src/pages/compare/[table].astro` 或对应条目（嵌图，其上保留数据表作为可回源/可校验的「图例+原文」）；`src/styles/global.css`（svg 内字号/颜色变量绑定，跟随双主题）。`verify-escape-guide.sh` 需加「svg 内数字 == compare.json 数字逐字一致」不变式（与既有「表↔条目逐字一致」同风格，见 `compare/[table].astro:3-4` 注释）。
- **成本**：**中**（要写一个坐标/刻度生成器并对齐 4 套数据；刻度标签挤压的调试是脏活，见 §4 目检清单）。
- **预期收益**：**中高**（图是「扫读层」的自然载体，直接补缺陷二说的「5 秒层」）。但**不替代表格**——表的可校对性必须保留，图是「看」，表是「核」。
- **破零 JS**：**不破**（内联 SVG 无脚本）。需防：SVG 文本若被用户选中复制，不得破坏「逐字一致」守护（守脚本按文本节点比对即可）。
- **与 U 系列的关系**：U-1 的「大数字」是单点、R-C 是分布；U-5（对照表行深链）已落地，R-C 图与表在**行的层面联动**（点图一条 → `#rowId` 锚点跳回表行）。

### R-D · 对照表多视图 + 切片筛选（结构化 JSON 的二次开发）

- **解决**：缺陷一/三在**集合层**的残余。四张 compare 表当前每张一屏全列（`compare/[table].astro:57-83`），虽已加行深链/卡片化/争议小标（P1-12/U2-M6/P-13），但**每列只有一个视角**：crashes 固定「事件→起点→终点→跌幅→恢复→机制」，不能「按跌幅降序」「只看 A 级」「只看恢复 ≤5 年」。
- **页面草图 / 多视图**：
  ```
  表头加切片 chip（零 JS = 构建期生成排序/分组的锚点视图）：
  [按跌幅] [按恢复年数] [仅 A 级] [仅 B 级]   ← 每个是同一张表不同排序/过滤的静态切片
  ```
  - 零 JS 方案：构建期为每个切片生成一个 `<section>` 或锚点分组（同数据、不同行序/过滤），用户点 chip 跳锚点，不重跑任何东西。
  - 破零 JS 方案（**标注：需红队裁决**）：一个 `<select>` 或几个 `<input type=checkbox>` + ≤2KB 原生 JS 在客户端排序/过滤 `json` 里的行；数据已在 JSON 里，本质是「重排 DOM class」，零索引零服务端。
- **涉及文件**：`src/data/compare.json`（数据已够，可能加 per-row 的 `sortKey`/`tags` 可选字段）；`src/pages/compare/[table].astro`；`src/styles/global.css`。
- **成本**：零 JS 方案 **小**（构建期多种行序，重复渲染同一数据）；破零 JS 方案 **小**（一次性 JS 预算 1–2KB）。
- **预期收益**：**中**。「按跌幅降序」是散户看 18 场股灾的第一个问题，现在答案要靠逐行目扫。
- **破零 JS**：默认方案**不破**；给一个可选**破**（`<select>` 切片）交红队裁决——理由在下节统一列。
- **与 U 系列的关系**：U-5 已给「行级深链」，R-D 给「跨行切片」，两者正交叠加。

### R-E · PATH 导览卡流产品化（把四条路径做成可翻页的线性导览）

- **解决**：缺陷二 + P-05 的残余（路径在离开首页断——U-4/P2-C3 已用条目页顶部 chip 补了「PATH 0X · n/m → 下一步」，但**路径本身仍不是一个可独立发送/独立消费的产物**）。
- **页面草图**：为每条 PATHS（`index.astro:101-132` 四条 + `src/lib/paths.mjs`）生成一个 `/guide/<n>/` 页面：
  ```
  ┌ 导览头：PATH 02 · 被套的人 · 4 步 ────┐
  ├ 卡 1/n：标题 + 一句话「这步解决什么」+（复用该条目的 5 秒层：大数字/风险）│
  ├ 卡 2/n：…（每卡即一屏，纵向滚动 = 翻页）│
  └ 底部：回到 PATH 索引 ─────────────────┘
  ```
  卡片流本质是把 U-4 的 chip 行扩成「每步一个完整卡面」，数据全部现成（`PATHS` 常量 + 每条的 lede/when/maxRisk）。
- **涉及文件**：`src/pages/guide/[n].astro`（新增）；`src/lib/paths.mjs`（已存在，直接消费）；`src/styles/global.css`（卡流样式）。
- **成本**：**小**（构建期聚合既有数据，无新数据源）。
- **预期收益**：**中**。四条路径是站里最强的「动线」，产品化后可作为单一 URL 被分享（「被套了从这套开始戳」），也根治「路径散在四条互相独立的链接里」。
- **破零 JS**：**不破**。
- **与 U 系列的关系**：U-4 是「散点 chip」、R-E 是「聚合成一路导览」，同一份 `paths.mjs`，两种产品化深度。

## 3. 对零 `<script>` 不变式的立场与「破口」清单（交红队裁决）

硬约束现状 `src/styles/global.css:3-4`「零 JS」+ 实测全站 0 `<script>`。我**默认全部方案不破它**（R-A/R-B/R-C/R-E 破不了；R-D 默认方案不破）。但作为一个「激进重构派」，我必须诚实地把「值得破的破口」摆出来，因为 R-B/R-D 的**交互上限**被零 JS 压得很低：

| 若要破 | 用途 | JS 预算 | 为什么值得讨论 | 我的裁定倾向 |
|---|---|---|---|---|
| R-D 切片 | 对照表客户端排序/过滤 | 1–2KB | 18 场股灾按跌幅排序是高频且零 JS 下只能静态切片×N | **可以不破**（静态切片够用，先不破） |
| R-B 计算器 | 凯利/回本实时输入 | 1–3KB | 真「输入我的数」体验远好于查表 | 倾向**暂不破**，先用查表；若 3 个月后数据无提升再议 |
| U-2 方案 B 过滤框 | 别名即输即筛 | 2–3KB | 队长已裁定**方案 A（零 JS 拼音跳格）**，不复议 | 维持队长裁定 |

**结论**：本次无一方案*必须*破零 JS。若红队认为「查表/静态切片」的用户体验仍不达标的，破口从 R-B 计算器开最小，且全站 JS 预算应设上限（≤5KB、无依赖、无索引、无服务端——与 `global.css:1-4` 的站点气质一致）。**此决策权不在我，在主编 + 红队。**

## 4. 渲染判断分界：哪些「留浏览器目检」，哪些 headless 可代验

> 接住 `~/.dsh/AGENTS.md` 纪律 #2：UI 渲染层无法 headless 代验时显式标注，不用 HTTP 200/结构存在冒充页面正确。以下是我（本方案作者）的**自设验收边界**逻辑，供下游落地者直接抄。

### 4.1 headless 可代验（结构/数据，shell + 脚本即够）

这些是「事实存在/数量/一致」类，机器可判，**不依赖真实渲染**：

1. **零 JS 不变式**：`grep -c "<script" dist/**/index.html` 恒 0（含 aliases/guide/calc 新页）。
2. **SVG 零脚本 + 数字逐字一致**（R-C）：每个产出页内 `<svg>` 无 `<script>` 子孙；`svg` 内出现的数字集合 == `compare.json`/对应条目的数字逐字子串集合（复用 verify 脚本「逐字一致」方法论）。
3. **分型渲染落点**（R-A）：按 layer 分类的条目在 dist 里出现对应形态类（如 `.layer-执行` 页含 `details` 包裹的正文、理念页正文无折叠）——grep class 与结构即可。
4. **预计算表正确性**（R-B）：`calculators.json` 矩阵值 == 用独立公式重算的结果（不读生成器的输出，防止「修显示值不修生成器」）（例如凯利表逐格 `p-(1-p)/b` 重算、回本曲线 `1/(1-d)-1` 重算）——纯算术，headless 完全可做，且是**必须做**的（防构建期算错）。
5. **行深链/锚点 id 唯一性**（R-D/U-5）：一页内 `<tr id>`/`<h3 id>` 无撞 id；切片 chip 的 `href="#..."` 指向存在的锚点。
6. **对比度**（沿用审计 §2.4）：任何新增前景/背景色对（SVG 文字、calc 面板）用脚本算 WCAG 比值 ≥ AA。
7. **五节闸门不变式**（R-A 前置条件）：改渲染外壳后 122/122 条仍含 `mod-howto/plain/gain/source/notes` 五 section、四段式 `howto-when/steps/output/pass`（沿用审计 A 附录脚本）。

### 4.2 留浏览器目检（像素/观感/引擎差异，机器判不了）

这些是「看起来对不对」类，**必须**在真实浏览器（至少 320/375/414/1280 四档 + 亮暗两主题 + 一 iOS Safari + 一 Chromium）确认：

1. **R-A 折叠后的「扫读层」是否真的一屏可扫**：执行层「结论 + 步骤卡」在 375×667 是否放得进 1–2 屏；`<details>` 展开时 sticky 结论条 + section-chips 与分型外壳的**总 sticky 高度是否挤压正文**（这是审计附录 A 第 9 条「U-1 结论条窄屏挤压」的升级版，R-A 后最危险）。
2. **R-B CSS `:has(:checked)` 勾选计数**在 iOS Safari 15.4 以下/旧内核的降级观感（退化应「无计数但可勾」，不能「表格塌掉」）。
3. **R-C SVG 中文标签在 320px 的挤压/重叠**：刻度标签、负数符号、百分比位数溢出（这是 SVG 最大的坑，必须上真实字体渲染量，headless 截图 ≠ 本机真实中文字体）。
4. **R-C SVG 双主题观感**：svg 文字与格子色要随 `prefers-color-scheme` 走 CSS 变量，暗色下对比度/视觉噪音需目检（脚本能算比值，但「图上文字挤不挤」算不了）。
5. **R-E 卡流在长触屏上的「一屏一卡」节奏**：卡片高度 vs 视口高度的吻合度，断点处是否出现「半张卡」割裂。
6. **R-D 静态切片 chip 行**在 375px 是否横溢（沿用 P-01 同款 `.section-chips` 横向滚动手法后仍需目检确切断点）。
7. **打印/`prefers-reduced-motion`/Ctrl+F 对 `<details>` 折叠内容**的既有目检项（审计附录 B），凡 R-A 默认折叠正文，这些项的影响面扩大，需一并重目检。

### 4.3 一句话交付纪律

结构、计数、算术、唯一性、对比度 → **headless 脚本守着，CI 过才算过**；视口、折叠、挤压、字体、主题观感 → **留浏览器目检，交付报告里逐项标「未目检/已目检@设备」**，不得拿「dist 页面结构存在」冒充「页面正确」。
